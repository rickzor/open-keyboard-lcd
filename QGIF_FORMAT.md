# Independently observed QGIF format

This describes files generated by the RT82's image tools and interpreted by this
project. It is not a manufacturer specification. The encoder in `qgif.py` was
written independently from byte-level experiments with small solid images,
individual pixels, color ramps, and multi-frame animations. No vendor encoder
implementation or generated C code was copied.

## Header (10 bytes)

| Offset | Bytes | Observed meaning |
| --- | --- | --- |
| 0 | 4 | ASCII `QGIF` |
| 4 | 1 | Zero in the supported variant; other variants are not implemented |
| 5 | 1 | `2 * FPS - 1`; supported FPS is 1–128 |
| 6 | 2 | Frame count, big endian |
| 8 | 1 | Width / 4 minus 1 |
| 9 | 1 | Height / 4 minus 1 |

Dimensions must be divisible by four and at most 1024. The RT82 uploader uses
240×136, preprocessing the physical 240×135 screen size as the website does.
The low bit of byte 5 was always one in the tested variant; its general meaning
is unknown. FPS values beyond 128 wrap in the reference encoder, so this client
clamps GIF conversion instead of generating wrapped rates.

## Frame records

Partition the image into 4×4 blocks, ordered left-to-right and then top-to-bottom.
Each record begins with `ceil(block_count / 8)` bitmap bytes. Bit 7 of byte 0
corresponds to block 0. Set bits indicate that an eight-byte block follows;
unchanged blocks retain their previous decoded values. Changed blocks are packed
in increasing block order after the complete bitmap.

The initial record supplies every block. There is one record per image frame,
plus a final record that restores the initial image from the last frame. Even a
static file has this final, all-zero bitmap. The final reset record is not
included in the header's frame count. There is no observed trailing sentinel.

## Eight-byte color blocks

| Offset | Bytes | Meaning |
| --- | --- | --- |
| 0 | 2 | RGB565 endpoint A, little endian |
| 2 | 2 | RGB565 endpoint B, little endian |
| 4 | 4 | Four rows of two-bit palette indices, most significant pair first |

RGB565 has five red bits, six green bits, and five blue bits. The observed palette
is A, B, (2A+B)/3, (A+2B)/3. Each selector row covers four pixels from left to
right. This resembles the color blocks in DXT1, but selector byte ordering and
the animation container are handled explicitly by this implementation. Arbitrary
variants, transparency modes, and endpoint-order-dependent modes are not claimed.

The independent encoder chooses the most distant pair of colors in each block,
quantizes the endpoints to RGB565, and chooses the nearest palette entry for each
pixel. Colors are lossy; the endpoint-fitting algorithm is our own and may yield
a different size or appearance from the manufacturer's encoder.

## Evidence and limits

Hand-calculated fixtures cover solid colors, selector positions, interpolation,
bitmaps crossing byte boundaries, repeated frames, and loop restoration. A local
reference decoder also parsed the earlier vendor-generated 24-frame animation.
Hardware verification must include looking at the actual keyboard: HID write
acknowledgements alone cannot prove the LCD decoded an animation correctly.

This encoder does not solve the separate single-slot flash-erase limitation
recorded in [PROTOCOL.md](PROTOCOL.md).
